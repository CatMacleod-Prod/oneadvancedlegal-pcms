# Distributed Redis Caching for Matter Files & Timelines

## Strategic Context
In active law practices, fee earners frequently re-query active case timelines, client contact profiles, and recent correspondence records throughout the working day. Direct database retrieval for repeated read-heavy requests generates unnecessary database load and elevates latency across multi-office practices. Implementing a distributed Redis caching layer for active matter records and timeline feeds reduces perceived data retrieval time to under 200ms and significantly unburdens the primary transactional database.

## Success Criteria
- Cache hit ratio of 75% or higher on active matter timelines and fee-earner workspace queries.
- Read response latency for cached matter data reduced to under 50ms.

## Scope

### In Scope
- Deployment and clustering of managed distributed Redis cache instances.
- Cache-aside implementation for matter overview data, user permissions, and timeline feeds.
- Cache invalidation and mutation handling on matter update events (event-driven via message bus).

### Out of Scope
- Persistent storage of audit logs or sensitive unencrypted financial ledger entries in cache.

## Acceptance Criteria
WHEN a fee earner opens an active matter file, the PCMS API Gateway SHALL retrieve timeline and metadata from Redis cache within 50ms on cache hit.

WHEN a matter update or new email filing event occurs, the Cache Invalidation Service SHALL invalidate and refresh the affected matter cache keys within 100ms.

IF the Redis cache cluster is temporarily unreachable, the PCMS API Gateway SHALL fallback gracefully to direct database queries without returning user errors.

## Business Rules
- Time-to-Live (TTL) for active matter caches must be set to 60 minutes with sliding expiration on active reads.
- Cached payloads containing Personally Identifiable Information (PII) must be encrypted at rest and in transit.

## Dependencies
- Redis Cluster deployment and network peering with PCMS application virtual private cloud (VPC).
