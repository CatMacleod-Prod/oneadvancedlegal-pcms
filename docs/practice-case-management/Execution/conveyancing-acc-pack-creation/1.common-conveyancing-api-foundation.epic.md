# Common Conveyancing API Foundation

## Strategic Context
Conveyancing property and financial data across PCMS currently lack a unified API layer, forcing integrations to rely on direct database calls or duplicated workflow-specific code paths. Delivering this shared foundation establishes the critical path infrastructure, entity extensions, idempotency mechanisms, and core lifecycle endpoints (property, finance, exchange, completion, completion statements, orders, and documents) required to support all subsequent workflow-specific suites.

## Success Criteria
- 100% of Tier 1 shared endpoints (10 endpoints) and Tier 2 modifications (4 endpoints) deployed and passing end-to-end contract tests.
- Single unified ConveyProperty and ConveyFinance entity model operational across Sale, Purchase, and Re-mortgage workflows.
- Idempotency middleware active and verified across all mutation endpoints returning duplicate-safe 200 responses.

## Scope

### In Scope
- Idempotency middleware for header-based deduplication across all POST/PUT routes.
- ConveyancingController scaffold and OpenAPI documentation base.
- ConveyProperty entity extension (8 to 28 columns) and property GET/PUT endpoints.
- ConveyFinance unified GET/PUT endpoints and reference data lookup endpoints (key dates, search types, title guarantee types, local authorities).
- Exchange PUT and confirm POST endpoints with side-effect automation.
- Completion PUT, completion statement POST and GET endpoints.
- Modifications to existing endpoints: Orders GET/POST (search type validation and filters), Disbursements GET, and Documents POST (folderPath and deduplication).
- Email dispatch service scaffolding and completion.

### Out of Scope
- Workflow-specific business logic for Purchase legal forms (deferred to Purchase Suite).
- Land Registry OS1/AP1 partner integrations (deferred to Re-mortgage Suite).
- Direct cashier ledger postings (deferred to Completion Postings Epic).

## Acceptance Criteria
WHEN a client submits a mutation request with an existing Idempotency-Key header, the Conveyancing API SHALL return the cached response with deduplicated status without re-executing business logic.

WHEN a client requests property or finance details via GET /v1/matters/{matterId}/conveyancing/property or /finance, the Conveyancing API SHALL return the unified 28-column property schema or structured financial breakdown.

WHEN an exchange confirmation is submitted via POST /v1/matters/{matterId}/conveyancing/exchange/confirm, the Conveyancing API SHALL record the exchange milestone and trigger associated downstream letter generation tasks idempotently.

WHERE a completion statement is requested via GET or POST /v1/matters/{matterId}/conveyancing/completion-statement, the Conveyancing API SHALL return structured JSON totals for disbursements, receipts, and net balance rather than a document binary.

IF an invalid searchTypeId is provided in POST /v1/orders, THEN the Conveyancing API SHALL reject the request with HTTP 400 Bad Request referencing the /v1/search-types reference data.

## Business Rules
- Property PUT updates must validate against England & Wales jurisdictional rules (and Welsh LTT if enabled under decision D-05).
- Finance GET filtering using CalcTypeId must accurately isolate mortgage, disbursement, and receipt ledgers without cross-contamination.
- Documents POST folderPath parameter must create missing directory trees automatically within the matter DMS workspace.

## Dependencies
- Base PCMS matter data model and database migration framework.
- Authentication and authorization pipeline in oal-pcms-api.

## Open Questions
- Decision D-05: Final confirmation on whether Welsh Land Transaction Tax (LTT) specific fields are included in the shared ConveyProperty model.
