# Runtime Platform Detection & Host Routing

## Strategic Context
Mid-market law firms operate heterogeneous desktop fleets spanning Classic Win32 Outlook, New Outlook for Windows, Mac Outlook, and Outlook on the Web. To eliminate separate codebases and maintenance overhead, the Add-In must dynamically detect its host container at runtime and execute appropriate API pipelines while enforcing identical behavior and parity across all supported versions.

## Success Criteria
- Automated host environment detection executes in under 50ms upon add-in initialization across all host types.
- Single unified Add-In codebase deployed across Classic Outlook, New Outlook, Mac, and OWA with identical user workflows.
- All 18 previously passing legacy features continue to pass in Classic Outlook with zero regression.
- All features pass in New Outlook with zero regression from new platform routing changes.
- 100% test pass rate across all 7 target versions: Windows Classic 2608, 2607, LTSC 2408; New Outlook 1.2026.x.x; Mac 365 16.112.x; Mac LTSC 16.89/16.90+; and OWA.
- All existing features currently available in PCMS's Classic Outlook Add-In are retained unless explicitly superseded or documented as conflicting.

## Scope

### In Scope
- Host container runtime detection using Office.js context API (`Office.context.platform` and `Office.context.mailbox.diagnostics`).
- Dynamic routing to platform-specific adapters (Win32 extended property pipeline vs. Graph/Event-driven pipeline).
- Baseline regression test suites verifying 18 legacy features in Classic Outlook and full functionality in New Outlook.
- Compatibility across all 7 target Microsoft Outlook versions.

### Out of Scope
- Direct COM/VSTO native interop layer modifications (handled via Office.js web add-in runtime).
- Standalone platform-specific add-in distributions.

## Acceptance Criteria
WHEN the Add-In initializes in any Outlook client, the Platform Detection Module SHALL determine the host environment (Win32 Classic, New Outlook, Mac, or Web) within 50ms.

WHERE the host is identified as Classic Outlook (Win32), the Add-In SHALL activate the Win32 extended property pipeline for metadata capture.

WHERE the host is identified as New Outlook or OWA, the Add-In SHALL activate the modern Graph-compatible runtime pipeline.

IF an unsupported Outlook build or platform is detected, THEN the Add-In SHALL display a clear fallback notice instructing the user on minimum version requirements.

WHEN regression test suites are executed, the Test Automation Runner SHALL verify that all 18 existing Classic Outlook capabilities and all New Outlook features pass without failure.

## Business Rules
- On completion, there is a single version of the Add-In that behaves identically across Classic and New Outlook.
- Any further features added under this epic or future epics extending this Add-In must be delivered to both platforms; delivering to only one platform does not satisfy acceptance.
- All existing features currently available in PCMS's Classic Outlook Add-In must be retained, except where directly superseded by or conflicting with new Add-In functionality.
- Any feature supersession or conflict must be explicitly documented and agreed, not resolved implicitly.

## Dependencies
- Office.js Mailbox API requirement set 1.8+ across all target clients.
- Centralized deployment access via Microsoft 365 Admin Center.
